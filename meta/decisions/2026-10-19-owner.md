## O-30 A `./scripts/check` run's timeout is 30 minutes, with the wait rule

Asked: the owner, in this Project's chat, 2026-10-18 (agreed with the hands
chat), after HF-015 and HF-016.
- `./scripts/check` took 1168 s to 1317 s at mission 20 U1, past the
  20-minute explicit timeout the sub-agents passed. The harness then moved the
  run to the background, where the sub-agent had no sanctioned way to wait.
- The builder and aux roles now run with `BASH_DEFAULT_TIMEOUT_MS` and
  `BASH_MAX_TIMEOUT_MS` at 2700000 (45 minutes), so an explicit timeout below
  that is honoured.

Decided, from the switch brief of O-29 on:
1. **The timeout.** Every `./scripts/check` run is one foreground call with an
   explicit timeout of 1800000 ms (30 minutes). That is the value of the
   template's `<the gate's timeout, in ms>`.
2. **The wait.** Every long run (`./scripts/check`, `./scripts/gate`,
   `./scripts/speed`) follows the template's wait rule:
   - the command ends with an exit marker, `; echo "check-exit=$?"`;
   - a run the harness moves to the background anyway is waited for with one
     foreground `until grep -q '^check-exit=' <file>; do sleep 5; done` with
     an explicit timeout;
   - never a `sleep` of 25 seconds or more as a command's first statement,
     never Monitor or a background task;
   - never a report before the run has ended.

   This replaces decision 176's poll.
3. **What stays.**
   - O-2: each `./scripts/gate` item is its own foreground call with a
     20-minute timeout, and an item that does not finish within it is FAIL.
   - O-27: the 15-minute stop for an M1 item.
