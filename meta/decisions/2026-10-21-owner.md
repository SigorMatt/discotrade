## O-32 D-025: the speed ratio is measured in CPU time, and a run is void only on unequal load

Asked: finding D-025 (11d9134), mission 22 U5's retry under O-28.
- The bounded recompute was built, O-28 item 5's test passes, and G1.3 took
  694 s.
- Decision 170's three runs gave ratios 1.197, 1.347 and 1.295, a median of
  1.295 against the limit of 1.25.
- Another project's pytest (`/home/msi/git/hands`) was running at the end of
  every one of those runs.
- On the same machine in the same hours, the U5 tree with the weekly step
  switched off gave 1.299, and U4's code gave 1.127.

"Direction (for the architect). Either U5's measurement is taken again on a
machine with no other test suite running (decision 170's condition widened
from "the three commands" to any load), with U5 counted as retried, or U5 is
marked blocked as O-26 item 4 says."

Decided: the machine runs several projects at once, so no rule based on
machine load can keep a wall-time ratio honest. The measurement changes to
CPU time.

1. **CPU time.** O-26 item 4's measurement (`./scripts/speed`, decision 156)
   measures CPU time:
   - **The cgroup.** Each `./scripts/speed` call runs in its own cgroup, made
     with `systemd-run --user --scope`.
   - **The day's figure.** At each day boundary the call reads `usage_usec`
     from that cgroup's `cpu.stat`, so the harness, the fork server and the
     sandbox children are all counted. A day's CPU seconds run from the
     previous day boundary of the same call to this one.
   - **The ratio.** It compares CPU seconds per subject-day over the first and
     last 30 calendar days of the G1.3 scenario, O-26 item 4's windows. It
     leaves out everything before the first day ends and the first day after
     any process start. The 1.25 limit stands.
   - **No fallback.** If a cgroup cannot be created or its `cpu.stat` cannot
     be read, the measurement stops with an error and never falls back to
     wall time. The builder then replies `VERDICT: question <the error>`.
   - **The backend.** The replay keeps the backend it uses today: the
     subprocess backend with its fork server, whose children run inside the
     cgroup. The measurement refuses a sandbox backend whose work runs outside
     the cgroup, such as a container, rather than under-count it.
   - **The fresh last day.** The fourth figure is measured in CPU seconds the
     same way and still has no threshold. Wall time may be printed beside any
     figure for information; it decides nothing.
2. **The load backstop.**
   - Through both measured windows, the measurement samples the one-minute
     load average (the first field of `/proc/loadavg`) every 30 seconds.
   - A run is void only if the two windows' average loads differ by more
     than 1.0.
   - There is no process check: other projects' tests are expected to be
     running.
3. **Void runs.**
   - A void run is recorded as void, with its load samples, and repeated. It
     is never counted for or against the unit.
   - Three void runs in one unit stop it. The builder replies `VERDICT:
     question <the void runs and their windows' average loads>`.
4. **The binding figure.**
   - It is the median of the first three valid runs at the commit, taken in
     order (decision 170).
   - A void run is repeated, but a valid run is never discarded or repeated,
     whatever its result.
   - Runs measured before this ruling, in wall time, do not count toward the
     three.
   - A median above 1.25 fails the unit as O-26 item 4 says: a first failure
     is retried once, a second blocks it.
5. **What the unit reports.**
   - each run's ratio, its load samples and the two windows' averages;
   - every void run;
   - the median;
   - the same ratio at the parent commit, so the margin under 1.25 is known.
     The parent's figure may be a single valid run, labelled as such.
6. **Where the new measurement is built.**
   - It is a change to `scripts/speed.py` and its tests, made as the first
     commit of U5's retry: a `scripts:` commit of its own, before U5's code
     is measured.
   - Its tests prove three things, with the cgroup and the load source
     replaced by fakes: the error with no fallback when no cgroup can be
     made; the void rule; the refusal of a backend outside the cgroup.
   - That commit gives no G1.3 time and no ratio of its own.
   - The parent's ratio is measured with this tool on U4's code (`91d1497`),
     the way D-025's control ran U4's code.
7. **U5.** Its retry's three wall-time runs (1.197, 1.347, 1.295) do not
   count. U5 stays on its retry under this measurement, and that retry is
   its last attempt: a median of its first three valid runs above 1.25
   blocks it, as O-26 item 4 says.
8. **Wall-time rules.**
   - The 20-minute cap stays a wall-clock timeout.
   - O-27 item 3's 15-minute stop for an M1 item: the item's call samples the
     one-minute load average every 30 seconds while it runs.
   - If a call takes more than 15 minutes and its samples average more than
     2.0, it is re-run once before anything is filed. The 2.0 is the call's
     own process plus the backstop's margin of 1.0.
   - The re-run decides. Above 15 minutes again, the stop applies as O-27
     item 3 says.
9. **The rule stands from now on.** From this file on, every measurement
   under O-26 item 4 and decision 170 is taken this way: U5's, U6's
   regression measurement, and later missions'.

Reason, which constrains later work: hands runs several projects on the same
laptop at once, by design. A wall-time ratio read there measures the
neighbours as much as the unit. CPU time charged to the run's own cgroup
measures the run. The load backstop voids the rare run whose two windows saw
different contention. The limit is unchanged. Giving a project a quiet machine
on demand is the hands Project's (finding HF-019).
