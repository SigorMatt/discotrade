94. **DESIGN §12.1: the static check.** `src/discotrade/validation/static.py`
    checks a source text with `ast` and returns either success or the
    first failure as a rule name and a message; the numbers come from
    `config/thresholds.toml` (`validation.max_lines`, `max_params`,
    `grid_max_params`, `grid_max_values`, I-10). (a) Order: the rules are
    checked in the order §12.1 lists them, and within a rule the first
    offending node in source order is named; a test pins the order with a
    text that breaks two rules. (b) Lines are physical lines (R-24). (c)
    `PARAMS` and `GRID` are each assigned exactly once at module level,
    by a plain assignment to the bare name. A numeric literal is an `int`
    or `float` constant, or unary minus applied to one; a `bool` is not
    numeric. `GRID` is a dict literal whose values are list literals of
    numeric literals. (d) `position` is a module-level `def position(bars,
    params)`: exactly those two positional parameters, no default, no
    `*args`, `**kwargs` or keyword-only parameter. (e) Imports: `import
    numpy`, `import pandas`, `import indicators`, each plain or aliased,
    and `from numpy import ...`, `from pandas import ...`, `from
    indicators import ...`; a dotted module (`numpy.random`), a relative
    import and every other module are refused. (f) The forbidden names
    apply to every identifier the text binds or reads: names, function and
    lambda parameter names, function names, import aliases and keyword
    argument names; the forbidden attributes apply to attribute access;
    the underscore rule applies to all of these and to attribute names.
    (g) Every file under `reference/` and the strategy fixtures named in
    the mission's tests as valid submissions pass; a reference file that
    fails is a finding, not an edit. The hostile suite that pins the list
    against attacks is step S2.2's (§12.5); a builder who finds a further
    trick adds the rule and its test (§12.1).

95. **DESIGN §12.4 with I-2, I-7 and decision 44 (finding D-006): the
    sandbox interface, the job and the runner.** (a) `sandbox/base.py`
    holds the `Sandbox` protocol, `SandboxJob` and `SandboxResult` (§12.4:
    a job is a source text or, for the in-process backend only, a function
    object; parameter sets; a mode, `positions` or `reverse_sample`; per
    instrument the bars of the window with their context; the limits. A
    result is, per parameter set, instrument and window bar, the target
    `p(t)`, the call times, or an error with its stage), and the harness
    function that builds a job for a window: per instrument, the stored
    bars of the window and the context before it up to `history_cap_bars`
    (decision 23), the roll gaps needed to adjust prices as of each bar
    (§5.6, decisions 24, 36, 37), `hour` and `weekday` in the calendar's
    time zone, `shorting`, and nothing later than the window's last
    trading day. A test asserts that a job built for W of a day `D` holds
    no bar whose trading date is after W's last day. (b)
    `sandbox/runner.py` is the program that runs inside a sandbox. It
    imports only the standard library, `numpy`, `pandas` and
    `discotrade.indicators` (a test reads its imports with `ast`), reads
    its job from an input directory, and writes its result as one JSON
    document on standard output. The job on disk is a format `numpy` or
    `pandas` reads without `pyarrow` (the image of step S2.2 holds no
    `pyarrow`), the builder's choice, stated in the commit body. (c) The
    runner loads the text afresh, in a namespace of its own, for each
    parameter set and each instrument (decision 44), with `indicators`
    bound as `strategy.py` binds it; builds each slice of §6.2 itself,
    prices adjusted as of the slice's last bar; and checks each result by
    decision 22's rule, clipping a negative result to 0 where shorting is
    not allowed. A test shows that its targets equal, exactly, those of
    `backtest.evaluate` for the three reference strategies on `test_mixed`
    over a window holding a SYNA roll, and that its result check agrees
    with `strategy.check_result` on a table of values. A test drives
    `tests/fixtures/strategies/cheat_lookahead.py` through the runner on
    every instrument of `test_mixed` and shows that each instrument's
    targets equal those of that instrument evaluated alone (D-006). (d)
    A result's error stages are `load` (the text raised while loading, or
    defines no callable `position`), `dry_run` (a call raised or returned
    a result outside the contract) and `limit` (wall clock, memory, output
    size); the sequence of item 98 maps `load` and `limit` to its stage
    `dry_run`. (e) An error text the runner or the
    harness returns for a submission names the stage, the rule and, for a
    bad result, the bar's index within the window and what was wrong
    (raised, not a number, not finite, out of range); it never holds an
    instrument symbol, a venue, a contract, a date, a timestamp or a
    price, because §12.2 sends it back to a worker (I-8, §13.2). A test
    checks every error text the mission's fixtures produce against the
    symbols, venues and contracts in `config/` and `tests/fixtures/config/`
    and against a date pattern. (f) `sandbox/inprocess.py` calls a Python
    function object directly for unit tests and refuses a job carrying
    source text. Approach execution in the day loop is not moved in this
    step (decision 48 still holds until step S2.2).

96. **DESIGN §12.4: the subprocess backend and `config/run.toml`.**
    `sandbox/process.py` runs `sandbox/runner.py` in a child process
    started with the harness's own interpreter in isolated mode, with its
    working directory a scratch directory of the job, resource limits set
    in the child (at least address space and CPU time), the job's
    wall-clock limit enforced by the harness, which kills the child, and
    standard output read up to a size cap. It accepts only a source text
    whose sha256 equals that of a file under the repository's `reference/`
    or `tests/fixtures/` (§12.4; a refusal names the rule) and passes no
    environment variable holding a key (I-13: the child's environment is
    built from an allow-list). It records call times and enforces only the
    wall-clock limit (§12.2). The limits are read from `<config>/run.toml`,
    table `[sandbox]` (DESIGN §3 names the file; it is not one of the
    frozen files of §4.3); the mission creates `config/run.toml` and a new
    `tests/fixtures/config/run.toml` with the same values, loaded by
    `config.py` into a frozen record with an unknown key refused. Only the
    code that builds a sandbox job requires `run.toml`, naming it when it
    is absent; nothing else does. `src/discotrade/sandbox/process.py` is
    added to `SUBPROCESS_FILES` of `tests/test_offline.py` (decision 47);
    the child is a Python program of this repository that opens no
    connection. Its refusal by `run-day` outside a synthetic replay is
    step S2.2's, which first gives the day loop a sandbox.

97. **O-17, DESIGN §12.2 stage 2 and R-23: the dry run and the grid on W.**
    (a) Combinations are the product of `GRID`'s values, keys in `GRID`'s
    declaration order and each key's values in declaration order, the
    other parameters from `PARAMS`; with no `GRID` the one combination is
    `PARAMS`. Each runs on W of the candidate's day `D` (§4.1) in the
    sandbox; every call must return a finite number in range (decision
    22), else the stage fails. The two call-time limits are enforced only
    when the backend says it enforces them (the container backend of step
    S2.2); the other backends record call times and enforce only the job's
    wall-clock limit. (b) The harness scores each combination's targets on
    W with `backtest.score`, outside the sandbox, and computes for it the
    plain and the exposure-adjusted Sharpe at 1x and at 2x. The adjusted
    series is O-4's with `W` the window: for each instrument `i`,
    `hbar_i(W)` is the mean of the evaluation's position `h(u)` over its
    window bars (0 with none) and `R_i(D)` the sum of the unit returns of
    decision 81 (b) over its bars of day `D` of the window; the daily
    adjusted value is the decision-23 daily net value minus the mean over
    the instruments of `hbar_i(W) * R_i(D)`. (c) That series is built by a
    new public function of `src/discotrade/paper.py`, `adjusted_rows`,
    which takes per-instrument evaluation rows in place of a subject's
    stored records; it and `paper.adjusted` compute the subtraction
    through one private function of `paper.py`, so that O-4 has one
    implementation, and `paper.adjusted` returns on every case of
    `tests/test_exposure.py` what it returns today. The audit of decision
    89 (b) accepts a call to `paper.adjusted` or to `paper.adjusted_rows`
    as the call O-18 asks for; its test gains a case showing an `adjusted`
    entry that calls neither failing. (d) The grid fixes the combination
    with the greatest adjusted Sharpe at 1x that is a number; on a tie,
    the first in the order of (a); when no combination's figure is a
    number, the first in that order. (e) The validation result carries
    `grid`, the trial row's value of decision 62: an object with `grid`
    (the text's `GRID`, or `null`), `fixed` (the fixed parameters) and
    `results`, one entry per combination in the order of (a) holding
    `params`, `plain` and `adjusted`, each an object with `sharpe` and
    `sharpe_2x` (`null` for a figure that is not a number); `metrics_w`,
    the §8 metrics of the fixed combination on W; and `adjusted_w`, of
    decision 86 (a)'s shape, for the fixed combination over W. Writing them
    to a trial row is step S3.2's. (f) The function that fixes the
    combination is registered `adjusted` in
    `tests/fixtures/return_readers.toml` (O-18's table: "the grid on W");
    `paper.adjusted_rows` is `producer`; any other function the audit finds
    in the validation package is registered `producer` or `display`, each
    named in the commit body.

98. **DESIGN §12.2 stages 3 to 5 and §12.3: determinism, activity, the
    correlation gate and the sequence.** (a) Determinism: the fixed
    combination is run again on W in a new job of the same backend and its
    targets must equal the first run's exactly; then a job in mode
    `reverse_sample` calls the function, inside one process, for a sample
    of each instrument's window bars in descending time order, each with
    its own slice, and the targets must equal the first run's for those
    bars. The sample is at most `REVERSE_SAMPLE` bars per instrument, a
    constant of the procedure that lives in the module (like decision 30's
    tolerance), drawn by `numpy.random.default_rng` seeded with the
    integer of the first 16 hex digits of the text's sha256. (b) Activity:
    the count, summed over the basket, of the fixed combination's window
    bars with `trade(u) > 1e-9` (the §8 floor, decision 25) is at least
    `validation.min_changes_w` (R-1). (c) The correlation gate: the
    submission's position series is the fixed combination's `h(u)` over
    W's window bars, concatenated over the basket in the track's
    instrument order; each live and dormant approach's series is the same,
    from its frozen source and fixed parameters under `approaches/<id>/`,
    run on the same W through the same backend; the state of an approach
    is decision 63's. The Pearson correlation is taken over the same bars;
    a pair in which either series has zero deviation is not a duplicate.
    An absolute correlation above `validation.corr_max` rejects the
    submission naming the approach with the largest absolute correlation
    (the lowest id on a tie). The approaches' series may be held in memory
    for one validation; nothing is written to the state directory. (d)
    The sequence (`validation/sequence.py`) runs the five stages in §12.2's
    order and stops at the first failure, returning its stage (`static`,
    `dry_run`, `determinism`, `activity`, `correlation`) and an error text
    under item 95 (e); a correlation rejection names the approach id (an
    id is not a symbol or a date). It reads only W's bars and their
    context; its result on success is item 97 (e)'s. Nothing calls it from
    `run-day` or `replay` in this step: the day's generation is step
    S3.2's, and the retry with the error text is §12.2's last paragraph,
    built there.
