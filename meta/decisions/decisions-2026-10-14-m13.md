102. **DESIGN §12.4: the container backend and its image.** (a)
     `sandbox/container.py` implements the `Sandbox` protocol with Docker or
     Podman: the one `run.toml` names in `[sandbox] runtime` (`"docker"` or
     `"podman"`), or, when the key is absent, the first of `docker` and
     `podman` found on `PATH`. No runtime found is a harness error naming
     it, never a rejection of a submission. (b) One container per job,
     started with: no network (`--network none`); a read-only root file
     system; a `tmpfs` at `/tmp` of `tmpfs_bytes`; a non-root user (the
     image's, also given on the command line); all capabilities dropped; no
     new privileges; a process limit of `pids`; a memory limit of
     `memory_bytes` with no swap beyond it; a CPU limit of `cpus`; the job's
     input directory as the only mount, read-only; an environment holding
     only a fixed allow-list written in the module, nothing taken from the
     parent (I-13); and a name the harness chose, so that it can kill and
     remove it. The harness enforces `wall_seconds` and on expiry kills and
     removes the container; it reads standard output up to `output_bytes`
     and discards standard error; it removes the container after every
     run, whatever the outcome. One function of `container.py` builds these
     options, and every run, the probe's included (item 103), uses it. (c)
     The backend accepts any source text, a worker's included (§12.4: the
     only backend allowed for one); it refuses a job carrying a function
     object. It says it enforces the call-time limits (decision 97 (a)), so
     the dry run of the validation sequence on it applies `call_p95_ms` and
     `call_max_ms`. (d) `config/run.toml` and
     `tests/fixtures/config/run.toml` gain, in `[sandbox]`, the keys
     `image` (the image's repository name), `pids`, `cpus` and
     `tmpfs_bytes`, and may carry `runtime`; the values are the project's
     own choice, the same in both files, with a comment saying so. No
     existing value of either file changes; `run.toml` is not one of the
     frozen files of DESIGN §4.3 (decision 96), so this is not a
     frozen-config change. `config.py` loads the new keys and still refuses
     an unknown key, naming it. (e) The image is defined under `sandbox/`
     (DESIGN §3): a Python base image pinned by digest, of the same minor
     version as the interpreter `uv` runs the project with; `numpy` and
     `pandas` pinned to exactly the versions `uv.lock` holds; the runner,
     the indicator library and the probe of item 103; a non-root user; and
     nothing else (no `pyarrow`, no `httpx`, no other module of
     `discotrade`). How the runner's `import discotrade.indicators`
     resolves in the image without `importlib.metadata` (REVIEW-12 note 6)
     is the builder's choice, stated in the commit body; the runner's
     targets in the image equal its targets on the host (the test of (g)).
     The image's tag is the configured `image` name with, as its tag, the
     first 12 hex digits of a sha256 over every input of the image (the
     definition file, the files copied in, the pins), so a changed runner,
     library or probe changes the tag. `discotrade sandbox build` builds
     the image of the current tag and prints the tag; when that tag exists
     it builds nothing and prints it. (f) Building the image fetches the
     base image and the two packages, as `uv sync` fetches the locked
     dependencies. It is a setup step the builder (and the owner on the
     server) runs; no test, no `./scripts/check` run and no gate runs it,
     and I-11 holds for every test: a test that needs the image finds it
     already built. Decision 47's list of subprocesses gains one entry: the
     container runtime's command, started only by `sandbox/container.py`,
     whose every `run` carries `--network none`; `container.py` is added
     to `SUBPROCESS_FILES` in `tests/test_offline.py`. (g) Tests that start
     a container carry a new marker `container`, registered with pytest.
     Outside a gate, such a test skips, printing the reason, when no
     runtime is found or when the image of the current tag is not present
     (the reason names `discotrade sandbox build`); under
     `DISCOTRADE_GATE=1` a skip is a failure, as for every gate test
     (DESIGN §18.1, §18.2; the REVIEW-1 note in `meta/BACKLOG.md`). The
     unit's tests, on the container backend: the targets of the three
     reference strategies on every instrument of `test_mixed` over the
     window holding the SYNA roll, for two parameter sets in one job, equal
     exactly those of the in-process runner; an endless loop returns
     `limit` at the wall-clock limit of a `run.toml` copied under the
     test's temporary directory with a short limit (said so), and no
     container of the job remains afterwards; an output over the cap
     returns `limit`; a memory bomb returns `limit` or a `dry_run` error;
     a fake key variable set in the parent is absent in the container; a
     source text that is not a repository file runs; the correlation stage
     compares a submission with an approach whose frozen source is not a
     repository file (REVIEW-12 note 5); a slow fixture fails the dry run on
     `call_p95` and one call above `call_max_ms` fails on `call_max`, at the
     production values; and the tag, computed by a pure function over a
     copy of the inputs, changes when the copied runner changes (no build).

103. **DESIGN §12.4, §18.3 G2.3 and §19.3 L5: the probe, `sandbox selftest`
     and `doctor --live sandbox`.** (a) The probe is a program of this
     repository, `sandbox/probe.py`, that imports only the standard
     library, is copied into the image (an input of its tag), and is
     started by the container backend with exactly a job's options (item
     102 (b)) and, as its mount, the input directory of a real job built
     for W of a day `D`. It does not run a submission. It writes one JSON
     document to standard output reporting: the routes of its network
     namespace (from `/proc/net/route`) and the interfaces present, and the
     outcome of a TCP connection attempt, with a one-second timeout, to an
     address of RFC 5737's TEST-NET-1 (so that nothing is reached even if
     isolation failed); the outcome of creating a file under `/`, `/usr`,
     `/home` and the mount, and under `/tmp`; its user and group ids and
     its effective capability set (from `/proc/self/status`); and the files
     of the mount with, per instrument, the count and the latest open time
     of the bars it holds. (b) The harness, not the probe, judges the
     report: the routing table holds no route, no interface but loopback
     is present, and the connection failed; every create outside `/tmp` failed and the one under `/tmp`
     succeeded; a non-zero user id and an empty effective capability set;
     the mount holds, per instrument, the job's window bars and context and
     no bar whose trading date is after W's last day. (c) `discotrade
     sandbox selftest` (with the common options `--state`, `--track`,
     `--config`, `--as-of`) builds that job for decision 19's `D`, runs the
     probe, prints one line per finding with PASS or FAIL, and exits 0 only
     when all pass; with no runtime or no image of the current tag it exits
     1 naming which, and starts nothing. (d) `discotrade doctor --live
     sandbox` (L5) runs the self-test; offline, without a runtime, it
     refuses clearly, names that no container runtime was found, exits 1
     and starts nothing (a test with an empty `PATH`). Decision 15's rule
     for the other check names stands. The self-test on the server is the
     owner's live check L5.

105. **DESIGN §12.4, §16.1 step 2 and §16.4: approaches in the day loop run
     behind the sandbox; decision 48's in-process path is replaced.** (a)
     The day function obtains an approach's targets for the bars of `D`
     from one sandbox job per approach and day, in mode `positions`,
     carrying its frozen source and fixed parameters and, per instrument,
     the bars the slices of those targets need (the bars of `D` and their
     context up to `history_cap_bars`, decision 23), the continuity of
     decision 49 unchanged. The targets go through the same executor, cost
     model and journal as before; a journal written through either backend
     equals, byte for byte, the one decision 48's path wrote (decision 80
     (a)'s method on the G1.3 scenario's first 30 calendar days, at the
     unit's parent and commit, the command and output in the body).
     `journal recompute` evaluates approaches the same way. (b) `run-day`,
     `replay` and `journal recompute` take `--sandbox container|process`.
     The default is `process` when every instrument of the track has a
     synthetic source (`adapter = "synth"`), and `container` otherwise;
     `process` asked for on a track with any other source is refused (exit
     2, naming DESIGN §12.4). This reads §12.4's "a replay on a synthetic
     source" as any run whose sources are all synthetic, a `run-day` on a
     synthetic source being a one-day replay; it breaks no invariant,
     because the subprocess backend runs only repository sources (I-7), and
     it keeps every existing test of the day on its synthetic tracks
     meaning what it meant. (c) A job error of stage `load`, `dry_run` (item
     101 (b)'s `no_result` included) or `limit` (wall clock, memory,
     output) for an approach is
     decision 63 (1)'s failure: the approach is retired with reason
     `failure: <the error text>` (item 101 (a)'s text), its rows of `D` are
     not journaled, and the day goes on. A harness error (no runtime, no
     image, a source the subprocess backend refuses, a malformed result)
     fails the day naming the approach, and nothing of the day is moved
     into place. The call-time limits are not applied in the day loop
     (they are validation's, §12.2), so a day's result never depends on
     machine load (I-12). (d) Tests: the existing tests of the day, the
     replay and `journal recompute` pass unchanged on the default backend;
     a test marked `container` replays three days of `test_synth` with an
     approach on the container backend and finds the journal byte-identical
     to the subprocess backend's (not gate G4.6, which is step S4.3's); an
     approach whose call breaks the contract on one day is retired with the
     sandbox's error text; `process` is refused on a track holding a
     non-synthetic instrument (a fixture configuration copied under the
     temporary directory, said so); a harness error fails the day. (e)
     Speed: the unit's body gives the seconds per replay day of the G1.3
     scenario's first 30 calendar days at its parent and at its commit
     (decision 80 (d)'s method), and the projected G1.3 time. If the
     projection is above 10 minutes, the subprocess backend may start its
     children from a fork server: one process per run of the day loop that
     imports only the runner's modules, never runs a text, and forks one
     fresh child per job with the limits set in the child, a child never
     reused for a second job. Decision 80 (c) does not forbid that server.
     Nothing else may be done for speed here: approaches are never run in
     the harness's own process again. (f) Any function the change makes
     the audit of decision 92 find is registered `producer` or `display`
     and named in the body; an `adjusted` reader found unregistered is a
     finding first.
