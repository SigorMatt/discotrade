122. **DESIGN §13.5: the providers (`src/discotrade/workers/providers.py`).**
     (a) `ChatProvider` is the protocol of §13.5. `Completion` is a frozen
     record of `text`, `tokens_in`, `tokens_out`, `model_version` (the
     string the provider reports) and `raw` (a JSON-ready mapping, the
     response body only, never a header or a key). A transport failure, a
     status other than success, a body without the expected fields, a
     timeout or an exhausted corpus raises one exception class,
     `ProviderError`, whose text names the model and the kind of failure
     and holds no key. (b) `ScriptedProvider(directory, start=None)`: the
     directory holds one subdirectory per model, named by the model id
     with each `/` written `__`, holding response files `0001.md`,
     `0002.md`, ... in name order; `list_models()` gives the ids of the
     subdirectories, sorted; the provider keeps a cursor per model, and the
     k-th `complete` for a model returns its k-th file from the cursor's
     start (`start` maps a model to the number of its files already used,
     so that a replay resumed in a new process continues where it
     stopped; step S3.2b builds it from `calls.jsonl`). Token counts are
     `ceil(characters / 4)` of the messages' contents (in) and of the
     text (out); the version string is `scripted`. A missing file is
     `ProviderError`. (c) `OpenAICompatProvider(base_url, key, timeout,
     transport=None)` uses `httpx`: `list_models` is `GET <base_url>/models`
     (the `id` of each entry of `data`), `complete` is `POST
     <base_url>/chat/completions` with `model`, `messages` and
     `max_tokens`, reading `choices[0].message.content`,
     `usage.prompt_tokens`, `usage.completion_tokens` and the body's
     `model` as the version string. The key comes from `NEBIUS_API_KEY`,
     read by the code that builds the provider, never by the provider's
     callers, never logged, stored or put in a prompt (I-13); an empty or
     missing key, or an empty `base_url`, refuses construction with a text
     that names what is missing. Tests use `httpx.MockTransport` and open no
     socket. (d) `ClaudeWorkerProvider(executable, model, timeout)` runs
     one headless Claude Code call per `complete`: print mode, JSON output,
     a turn limit of one, every tool denied, a non-interactive permission
     mode and the model given explicitly, the prompt on standard input,
     the environment the harness's minus `NEBIUS_API_KEY`. The exact flags
     are read from `claude --help` on the builder's machine and recorded in
     the body and the report; where `claude` is not installed, the flags of
     SPEC §17's coordinator line are used, adapted to no tools, and the
     report says so under NOT PROVEN. It reads the result text, the token
     counts and the model from the JSON. `list_models()` gives the one
     model it was built with. It is tested against a fake `claude`
     executable written by the test under its temporary directory, which
     checks its arguments and replies with fixed JSON; a non-zero exit, a
     reply that is not JSON or a timeout is `ProviderError`. The file is
     added to `SUBPROCESS_FILES`. (e) `discotrade doctor --live workers`
     (live check L3) is added for its offline behaviour only: without
     `NEBIUS_API_KEY`, or with no `config/models.toml`, it refuses with one
     clear line and exits 1, making no request; with a key it builds the
     provider and prints the pool against the provider's model list (a test
     runs that path through a `MockTransport`, not the network). The rest of
     L3 (twenty replay days with the real pool) is step S3.2b's. (f)
     `providers.py` is the only module under `src/discotrade/workers/` that
     may import `httpx` or start a process; every other module there still
     imports nothing that reaches the network or a secret.

124. **DESIGN §13.6: the pool (`src/discotrade/workers/pool.py`).** (a) The
     day's pool for trading day `D`: the `pool = true` models in file order,
     each kept when the provider's `list_models()` for the day holds it,
     else replaced by its fallback when the list holds that, else dropped
     for the day with a health notice `model_skipped` (subject the model id,
     detail the fallback tried); a model removed under (c) is dropped
     without a notice. The list is read once per day. A failed list read is
     a health notice `model_list_failed` and the day makes no call. An empty
     day's pool makes no call and logs a health notice `pool_empty`. (b)
     Rotation: the model for a call on `D` in cell index `c` is
     `pool[(ordinal(D) + c) mod len(pool)]` over the day's pool, where
     `ordinal(D)` is the count of the track's trading days from the track's
     `epoch` up to and excluding `D`. A retry uses the first call's model.
     (c) Failure tracking, derived from `calls.jsonl` and nothing else, so it
     is rebuilt from the ledger (I-5): a model's counted calls are its rows
     with outcome `trial`, `duplicate` or `invalid:<stage>`; a failure is
     `invalid:<stage>`; `provider_error` and `budget` rows are not counted.
     After a day's calls, a model whose last `fail_window` counted calls are
     a full window with a failure share above `fail_rate` (both read from
     `config/thresholds.toml`) is removed from the next trading day on, for
     good, and the day raises one `model_removed` health event at level
     `alert` (subject the model, detail the window's counts). (d) The cell
     window: per cell, the counted calls of open models (every provider but
     `ClaudeWorkerProvider`) under the same rule. When a cell's window
     crosses above `fail_rate`, and `workers.claude_fallback` is true, the
     cell is served by the Claude worker from the next trading day; while
     it is false, the day logs one `cell_needs_fallback` health notice; it
     is logged again only after the cell's rate has been at or below the
     limit over a full window and crosses again. (e) The model's cutoff
     date, its maker and the version string of the call are what a trial
     records (§9.1, §10.2). (f) Tests: rotation over three models for 20
     trading days serves no cell always by the same model; a missing model
     is replaced by its fallback, a missing model without one is skipped
     with the notice; a model with failures above the rate over a full
     window is removed with one `model_removed` event and is never chosen
     again; a window not yet full removes nothing; the cell rule with the
     flag false logs the notice once; each threshold is read, at its
     production value, from `config/thresholds.toml`, and a copied
     configuration with another value changes the outcome.

126. **DESIGN §13.4 (storage), §13.7, §10.2 and R-25: the day's generation
     (`src/discotrade/workers/generate.py`, a module the layout of §3 does
     not list, because §16.1 step 5 is called from `daily.py` and the
     generation is the workers' part of it).** One function generates for a
     track, a day `D`, a cell and a brief, given the provider, the day's
     pool and a sandbox backend, writing call rows to the ledger location
     it is given (the day's staging directory when step S3.2b calls it) and
     returning either a validated candidate or nothing. (a) Call ids are
     `c` followed by the first 12 hex digits of the sha256 of
     `<track>|<D>|<attempt>`; attempts are 1 and 2. (b) Budget: before each
     call, the day's tokens (the sum of `tokens_in` and `tokens_out` of the
     rows of `D` in `calls.jsonl`, staged rows included) plus
     `worker_max_output_tokens` is compared with `worker_tokens_per_day`;
     above it, no call is made, a row with outcome `budget` and zero tokens
     is written, the day raises a `token_budget` health event at level
     `alert`, and the generation ends. (c) A response file
     `responses/<track>/<D>/<call>.json` that already exists is read and no
     provider call is made (I-6, DESIGN §16.2). Otherwise the call is made
     with `max_tokens = worker_max_output_tokens` and the response is
     written at once, atomically, before it is parsed, outside the staging
     directory (§16.2's exception): call id, date, cell, model, attempt,
     the messages sent, the completion's text, tokens, version string and
     raw body, JSON with sorted keys. A `ProviderError` writes a row with
     outcome `provider_error` and the generation ends; no retry. (d) The
     response is parsed (`workers/parse.py`); a parse failure is outcome
     `invalid:parse`. A parsed source goes through the validation
     sequence with the correlation gate (`validation/sequence.validate`);
     a failure at a stage is `invalid:<stage>`, a failure at the
     correlation gate is `duplicate`, and a pass is `trial`. (e) Retry
     (R-25: one retry in all): after `invalid:<stage>` or `duplicate` on
     attempt 1, attempt 2 sends the first prompt, the first response as
     the assistant's message, and a user message with a fixed retry text
     and the error text (§12.2's text, fit to send back; for a duplicate,
     the id of the approach it duplicated and the limit). Attempt 2's
     outcome ends the generation. (f) Every call row has the keys of
     decision 62 and §10.2; the candidate returned carries the source, the
     description, the fixed parameters, the grid and its results, the
     metrics on W, the model id, its version string, its cutoff date as
     used, and the profile version, for step S3.2b to score on T. (g)
     Tests, on `test_synth` with the scripted provider and fixture
     responses under a new `tests/fixtures/responses/` (one subdirectory
     per fixture model): a valid response gives a candidate and one
     `trial` row; an invalid one then a valid one give two rows and the
     retry's messages hold the error text; a duplicate of a live approach
     then a second failure give two rows and the retry names the approach;
     a parse failure is stored in full before it is refused; a budget
     reached makes no call, writes a `budget` row and the `token_budget`
     event; a day whose response files exist makes no provider call (a
     provider that raises when called) and gives the same rows; a
     provider error writes one row and no retry; the same inputs give the
     same bytes twice. The validation in these tests runs on the
     subprocess backend, which accepts a text only when it is byte-identical
     to a trusted repository file (decision 104 (d)), so each fixture
     response's Python block is byte-identical to a strategy file under
     `tests/fixtures/strategies/` (an existing one, or a new one added
     there); one test marked `container` runs one fixture response through
     the container backend.
