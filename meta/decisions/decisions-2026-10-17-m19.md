150. **The one-sided t-test (DESIGN §15.1 `rank_persistence`).**
     `stats.py` gains the upper-tail probability of Student's t, `t_sf(t,
     df)` (the name is the builder's), written with `math` and `numpy`
     only. No dependency is added (CLAUDE.md). The regularized incomplete
     beta by continued fraction is one method; any exact method will do.
     Unit tests against values the test writes as literals or computes in
     closed form, without calling `t_sf`:
     - `df = 1`: `t_sf(1, 1) = 0.25` and `t_sf(0, 1) = 0.5`, to 1e-12;
     - `df = 2`: `0.5 * (1 - t / sqrt(t*t + 2))` at `t` = 0.5, 2 and 5, to
       1e-12;
     - `df = 3`: `0.5 - (a + sin(a) * cos(a)) / pi` with `a = atan(t /
       sqrt(3))`, at `t` = 1 and 3, to 1e-12;
     - the one-sided 5% critical values `t_sf(2.015048373, 5)` and
       `t_sf(1.795884819, 11)` equal 0.05, to 1e-6;
     - `t_sf(-t, df) = 1 - t_sf(t, df)`.

     Seen to fail: the two-sided probability returned in place of the
     one-sided one.

152. **Alert state, payloads, the other rules, health alerts, and the day
     loop (DESIGN §15.1 to §15.3, §16.1 step 6, §16.2; I-6, I-10, I-12).**
     (a) State. `alerts/<track>/state.json` holds `date` (`D`) and
     `alerts`, an object keyed `<kind>|<subject>`. Each entry holds:
     - `active`, whether the condition holds on `D`;
     - `since`, the date it last turned true, or `null`;
     - `value` and `threshold`, the rule's current figure and the threshold
       it is compared with, `null` where the rule was not evaluated or has
       none.

     A finding rule writes one entry for each subject it evaluates. A
     health kind writes one for each subject it has raised. The file is
     written as `ledger.line` writes an object (keys sorted, no whitespace,
     a newline), atomically, in the staging directory, on a new day only,
     so a re-run of a finished day writes nothing (I-6). The dashboard
     reads the rules' figures from this file and never recomputes them
     (SPEC §13: "from the same state files the alert rules read").
     (b) Firing. An alert fires on `D` when its entry is active on `D` and
     was not active, or did not exist, in the state of the day before
     (DESIGN §15.3). Each firing writes one payload file,
     `alerts/<track>/payloads/<D>/<kind>/<subject>.json`, where `<subject>`
     is `urllib.parse.quote(subject, safe="")`. The payload holds every
     number behind the alert, the thresholds in force (each key as the rule
     read it, with its value), and for an approach the fields of item 151
     (a). Payloads are written in the staging directory and never
     rewritten. Every threshold comes from `setup.thresholds` (I-10), and
     `alerts.py` names, in one module constant, every threshold key each
     rule reads (item 153 (d)).
     (c) `rank_persistence`. The subject is the track name. The rule takes
     the `timing` values of the last `alerts.rank_blocks` rows of
     `rank_persistence.jsonl` whose `timing` is not `null` (item 149 (b)).
     It is not evaluated with fewer. Otherwise `t = mean / (s /
     sqrt(n))`, with `s` the sample deviation (ddof 1), and `p = t_sf(t, n
     - 1)`. The condition is `p < alerts.rank_level`. With `s = 0` the rule
     is not evaluated (the design is silent; this is the simplest reading).
     The state's `value` is the mean, and the payload adds `t`, `p` and the
     block numbers.
     (d) `revival`. On `D`, for each lifecycle row dated `D` from `dormant`
     to `live`, the rule counts the approach's dormant trading days the way
     lifecycle step 3 counts them for `lifecycle.revival_min_dormant_days`,

     `alerts.revival_min_days`. The subject is the approach id. The rule
     reads no observation, so the clean rule of DESIGN §11.3 does not apply
     to it (O-18 counts it among events). Its payload carries the clean and
     exposed counts all the same.

     - `few_valid_candidates`: on a day whose run reaches step 5 with a

       `alerts.min_valid_candidates` rows dated in the last
       `alerts.valid_candidates_window_days` calendar days ending `D`, once

     - `cost_stale`: one event per `checked` date of the track's fee and

     1. the rank rows of item 149;

     4. the state and the payloads, in the staging directory.
