156. **The measurement of O-26 item 4: `./scripts/speed`.** (a) The
     command is `./scripts/speed --work <dir>`, a new executable under
     `scripts/`. Any Python it runs lives under `scripts/` too, run with
     the project's environment; no module is added under `src/` for it.
     `<dir>` is outside the code repository (I-14); the command refuses a
     path inside it. It replays the G1.3 scenario on the gate
     configuration exactly as `tests/gates/test_g1_3_lifecycle.py` sets it
     up: track `test_synth`, `tests/fixtures/config/` with
     `thresholds_gate.toml` in place of the thresholds as the gate copies
     it, the candidates file `tests/fixtures/scenarios/g1_lifecycle.jsonl`,
     from 2019-06-03 to 2020-06-10, in process, through the function the
     console script calls. If the gate's set-up differs from this in any
     way, the gate's wins and the unit says how.
     (b) Each call is one foreground call with a 20-minute timeout. On its
     first call the command creates `<dir>/state` with `init-state` and the
     configuration copy; on every call it continues the replay from the day
     after the last journaled day, in one process, until a day ends past
     its own budget (`--budget-seconds`, default 1020) or the replay is
     done. Before replaying 2020-06-10 it copies `<dir>/state` whole,
     `.git/` included, to `<dir>/before-last`. For each replay day it
     appends one line to `<dir>/days.jsonl`: the date, the seconds from the
     end of the previous day of the same process to the end of this one
     (for the first day of a process, from the process's start), the
     process's number, and the subject count, the number of distinct
     `subject` values in that day's decision-journal rows. It reads time
     with `time.perf_counter` and writes nothing in the state directory
     (a measurement, not a result: I-12 holds). A call that stops early
     prints `speed: continue <done> of <total> days` and exits 0.
     (c) When the replay is done, the command runs 2020-06-10 again in one
     fresh process (`discotrade replay` on `<dir>/before-last` for that one
     day, through `subprocess`), times its wall time, and prints, in this
     order:
     - `speed first30: <x> s per subject-day (<n> days counted)` over
       2019-06-03 to 2019-07-02;
     - `speed last30: <x> s per subject-day (<n> days counted)` over
       2020-05-12 to 2020-06-10;
     - `speed ratio: <last30 / first30>` to three decimals;
     - `speed fresh last day: <x> s`;
     - `speed process starts: <the first date of each process>`;
     - `speed: done`.

     A day counts unless it is the scenario's first day or the first day of
     a process (O-26 item 4). A window's figure is the total time of its
     counted days divided by the total of their subject counts. The fresh
     process's state is not compared with anything.
     (d) `--cold` makes the command call the cache-clearing function of
     item 157 (b) before every day; it is used for item 157 (c) only and
     prints the same lines. `--from`, `--to` and `--budget-seconds` exist
     for the command's own test, which replays a three-day span with a
     budget that forces a second process and checks the counted days,
     the subject counts, the windows' arithmetic and the process starts on
     a `days.jsonl` it writes. That test is in the check and is quick
     (decision 140).
     (e) The figures are only comparable on one machine and one load: a
     unit measures its parent and its commit in the same session, one after
     the other, and says the load average. U1 measures its parent by
     running its new command's files, copied unchanged, in a worktree at
     the parent; nothing else in that worktree changes. The command
     therefore reaches item 157 (b)'s function only under `--cold`, so that
     it runs at a parent that has no such function.

163. **The Claude Code form of the coordinator (DESIGN §14.1 to §14.3;
     SPEC §17).** (a) `ClaudeCodeCoordinator` in
     `src/discotrade/coordinator.py` implements the three methods of §14.1,
     one headless `claude` call per task. The flags are read from the
     installed `claude --help` and the version string from `claude
     --version`, both quoted in the commit body and the report; SPEC §17's
     list is the target: `--bare -p`, `--output-format json`,
     `--max-turns`, `--max-budget-usd`, `--permission-mode dontAsk`, an
     explicit `--model`, and every tool denied by the means the installed
     help gives. A flag the help does not list is not used, and the body
     says which. (b) Settings come from a new `[coordinator]` table in
     `config/run.toml` (DESIGN §3: `coordinator.*` keys; not a frozen
     file): `binary` (default `claude`), `model`, `max_turns`,
     `max_budget_usd`, `timeout_seconds` and `propose_fixes = false`, each
     with a comment saying it is the project's own choice. `model` is a
     model name the installed help or documentation accepts; it is not
     verified until live check L4, and the owner confirms it
     (`meta/BACKLOG.md`). If an existing test requires the two `run.toml`
     files to hold the same values, `tests/fixtures/config/run.toml` gains
     the same table and nothing else changes in it, named in the body
     (item 146 (c)); no other file under `tests/fixtures/config/` changes.
     (c) The prompt for `choose_cell` holds the offered cells (name, live
     count, free slots, the weak flag) and the registry lines as quoted
     data, as `coordinator.registry_lines` gives them, and asks for one
     JSON object `{"cell": "<name>", "brief": "<text>"}` as the whole
     reply. The reply is the `result` field of `claude`'s JSON output. An
     exit status other than 0, a timeout, `is_error`, a reply that is not
     that object, or a cell not offered gives the scripted choice and a
     `coordinator_fallback` health notice naming the reason (§14.3, §15.2).
     The brief is capped at `coordinator.brief_max_chars` and sanitised as
     a registry description is. `write_digest` and `write_runlog_line`
     send the payload tables or the summary and return the reply's text;
     the day loop does not call them in this step (S4.2b). (d) The key
     comes from the environment and is passed to the child only through
     its environment; it never appears in an argument, a prompt, a log or a
     state file (I-13). (e) `run-day` and `replay` accept `--coordinator
     claude`; `scripted` stays the default (decision 137 (a)). Without a
     `[coordinator]` table, or with a key missing, `--coordinator claude`
     is refused before any day with one line and exit 2; a `binary` not
     found on `PATH` is refused before any day with one line and exit 1.
     (f) `discotrade doctor --live coordinator` (live check L4): without
     `ANTHROPIC_API_KEY` it prints one line naming the variable and exits

165. **The coordinator's token budget (DESIGN §14.3, §16.3).** Within one
     run of a day, the coordinator's tokens (the input and output counts of
     `claude`'s JSON output, the fields named in the body) are summed. A
     task that would start with the day's sum at or above
     `budgets.coordinator_tokens_per_day` is done by the scripted form, and
     one `token_budget` alert with subject `coordinator` is raised for the
     day, its detail holding the sum and the budget. A call whose reply
     takes the sum past the budget is used as it is (it was paid for).
     Journaling and scoring complete (§16.3). The scripted form counts no
     tokens. The day's sum is kept in the run's memory and in that event;
     its record on the run log or the digest is S4.2b's. Tests with the
     fake: a day whose first reply's tokens reach the budget does its later
     task by the scripted form and raises the alert once.
