178. **The issue sinks (DESIGN 15.4, 19.3 L6; I-11, I-13).** `IssueSink`,
     `FileIssueSink` and `GhIssueSink` live in `src/discotrade/digest.py`,
     the module DESIGN §3 gives to §15.4; no other new module is added.
     (a) `FileIssueSink(directory)` writes each issue as one file,
     `<directory>/<track>/<n>.md`, `n` the lowest positive integer whose
     file does not exist, written as four digits (`0001.md`). Its bytes:
     `title: <title>`, `labels: <labels joined by ", ">`, an empty line,
     then the body, ending with one newline. `open` returns the file's
     path as text. The sink is given its track when it is built.
     (b) `GhIssueSink` runs `gh issue create` with the title, the body
     (through a body file in a temporary directory outside the state
     directory, removed afterwards) and one `--label` per label, with the
     state directory as its working directory, so that `gh` takes the
     repository from the state repository's remote. The flags are read from
     the installed `gh issue create --help` and quoted in the commit body
     with `gh --version`. If `gh` is not installed on the builder's machine,
     the body says so, takes the flags from the GitHub CLI manual, and the
     report lists them under NOT PROVEN. The child is started in a new
     session and a timeout kills its process group, as decision 166 does
     for `claude`. Its environment is the harness's without the other
     services' keys (`workers.providers.WITHHELD_ENV`, as the coordinator's
     child is given, decision 163 (d)); the sink reads no secret itself. An
     exit status other than 0, a timeout or a start that fails raises
     `IssueError` naming the cause, never a secret. `open` returns the last
     non-empty line `gh` prints (the issue's address).
     (c) Settings: a new `[issues]` table in `config/run.toml`, not a
     frozen file, each key with a comment saying it is the project's own
     choice: `binary = "gh"`, `timeout_seconds = 60`, and `labels =
     ["discotrade"]`. An issue's labels are those, then `finding` or
     `health` (the alert's class: `finding` for the kinds of
     `alerts.FINDING_KINDS`, `health` for every other), then the alert's
     kind. If an existing test requires the two `run.toml` files to hold
     the same tables, `tests/fixtures/config/run.toml` gains the same table
     and nothing else changes in it, named in the body (as decision 163 (b)
     did); no other file under `tests/fixtures/config/` changes.
     (d) The option `--issues` of `run-day` and `replay`: `none` (no issue
     is opened), `gh`, or `file:<directory>`. `replay`'s default is `none`
     (the met gates' replays name no sink and open none; O-25). `run-day`'s
     default is item 186's. A `file:` directory inside the code repository
     or inside the state directory is a usage error before any day (exit 2):
     the issue files are not state files, so that a failed day leaves the
     state as item 182 says. `gh` with a `binary` not found on `PATH`, or
     with a state repository that has no remote named `origin`, is refused
     before any day with one line and exit 1, and nothing is called.
     (e) `discotrade doctor --live issues` (live check L6): with no `gh` on
     `PATH`, or with a `--state` whose repository has no `origin`, it prints
     one line naming what is missing and exits 1, making no call; otherwise
     it opens one test issue and closes it, printing what came back. Only
     the refusals are tested (DESIGN 19.3).
     (f) Tests, with a fake `gh` written by the test under its temporary
     directory and named by `binary` (no test runs a real `gh`; I-11):
     `FileIssueSink` writes the bytes of (a), numbers a second issue
     `0002.md`, and returns the path; the fake receives the title, the body
     file's content and each label in the order of (c); an exit status of
     1, and a fake that sleeps past the timeout and starts a sleeping
     grandchild, each raise `IssueError` (the grandchild is gone after the
     timeout); the option's refusals of (d); both refusals of (e). Seen to
     fail, each made alone and reverted: the labels' class dropped; the
     kill sent to the child only.

182. **The retry and `run_failed` (DESIGN 16.2, 15.2; SPEC §11; REVIEW-19
     notes 4 and 6; REVIEW-17 notes 3 and 4).** (a) Inside the run lock, a
     day whose steps raise (any `Exception` after the day's refusals of
     decision 51 and of `_unclosed` have passed) is retried once, from a
     clean staging directory, in the same process and under the same lock.
     A refusal of `D` before the day starts (not a trading day, not closed,
     before the last journaled day and not in the journal) is not a failed
     day: it is refused once, as now, with no retry and no `run_failed`.
     (b) A first failure that the retry repairs appends one `run_retried`
     notice (subject the track, detail the day and the first error's text),

     response and makes no second provider call (DESIGN 16.2).
     (c) A second failure discards the staging directory and leaves every
     state file unchanged except the health log and the stored responses.
     It appends one `run_failed` alert (subject the track, detail the day
     and both errors' texts), opens one issue through the command's sink
     (title `run_failed <track> <D>`, labels as item 178 (c), body the two
     errors; an `IssueError` appends `issue_failed`), and re-raises the
     second attempt's exception, so that the command exits 1 as it does now
     and an existing test that expects an exception type from a failing day
     still sees it. A replay stops at that day as it does now.
     (d) The health events of a day are appended at once (DESIGN 16.2's
     exception). An event the log already holds, byte for byte, is not
     appended again (`state.append_health` already does so), so a retried
     day's equal events appear once. Where the retry's event differs from
     the first attempt's, both stay (I-5) and the body names the kind.
